**Дата:** 2026-07-30 · **Проект:** `C:\dev\translation` · **Режим:** read-only
**Данные прода:** получены через `railway run node` (только SELECT), Railway PostgreSQL.

## Резюме (10 строк)

1. Реально наполнены **четыре** хранилища: `Rule` (1966, из них 1723 ACTIVE), `QAPair` (626 / 554 ACTIVE), `DocChunk` (228, все с эмбеддингами 1536), `Document` (44, все COMPLETED).
2. Порядок обращения жёстко зафиксирован в коде: **кэш → сценарный гейт → канонический Q&A-оверрайд → детерминированный guardrail → гибридный поиск (чанки+правила+Q&A) → общие знания ИИ**.
3. «Общие знания ИИ» — не первый и не второй источник, а **последний**: срабатывают только при `confidenceLevel === 'insufficient'` И отсутствии сильного Q&A-совпадения И прохождении regex-фильтра.
4. Приоритет «внутреннее над общим» соблюдается. Приоритет **внутри** внутренних источников — почти не соблюдается.
5. **Авторитетных Q&A всего 5 штук** (4 `HISTORICAL_ANSWER_AUTHORITY` + 1 `VOICE_ANSWER_AUTHORITY`) из 626. Остальные 621 — без метаданных, обычные.
6. **`VOICE_AUTHORITY` на правилах = 0 записей.** Весь механизм приоритета правил (буст +40/+20/+8, пункт 2в системного промпта, маркер в контексте) в проде мёртв.
7. Сценарное дерево покрывает **только апостиль** (6 узлов). Переводы, цены, легализация, истребование — сценариев нет, они идут «открытым поиском».
8. `answerSource` (`knowledge_base` / `general_ai` / `deterministic_guardrail`) **никогда не пишется в БД** — 0 из 849 ответов ассистента. Владелец продукта физически не может увидеть, откуда взят ответ.
9. Разрешения конфликтов между источниками нет: `detectRuleConflicts` написан, но нигде не импортируется. Consistency-gate проверяет ответ против *объединения* источников, а не источники между собой.
10. 46% ответов ассистента (392 из 849) имеют `confidenceLevel = insufficient`; в очереди `AIQuestion` 539 записей, все `OPEN`; `AnswerFeedback` пуст (0).

## 3. Карта: тип вопроса → какой источник должен → какой отвечает фактически

Прогон реальных условий из кода (regex скопированы дословно; проверено скриптом против прода).

### 3.1. «как получить апостиль на свидетельство о рождении»

| Проверка | Результат |
|---|---|
| Канонический Q&A-оверрайд | overlap **0.000** → мимо |
| Детерминированный гейт | **`needs_clarification` @ `apostille.zags`** — `mentionsApostille && zagsDoc && !notaryDoc && !opekaDoc`, регион не назван (`scenario-classifier.ts:299-326`) |
| Guardrail | не срабатывает (нет Москвы) |
| `isBureauTopic` | true |
| Охват базы по ключевым словам | rules **461**, qa **184**, chunks **97** |

**Должен отвечать:** общие знания (процедура апостиля общеизвестна) ИЛИ база.
**Фактически:** бот **не отвечает вообще** — задаёт кнопочный вопрос «Где был выдан документ?» (СПб / ЛО / Другой регион). Поиск не запускается (`:539-543`). В базе при этом лежит 461 подходящее правило.
**Вывод:** для владельца продукта это выглядит как «бот не знает». На деле это осознанный дизайн: апостиль на оригинал зависит от региона выдачи, и без региона любой ответ был бы враньём.

### 3.2. «сколько стоит перевод паспорта»

| Проверка | Результат |
|---|---|
| Канонический Q&A-оверрайд | overlap **0.250** (< 0.55) → мимо |
| Детерминированный гейт | **ни одно правило не сработало** → уходит в LLM-классификатор |
| Guardrail | нет |
| `isBureauTopic` | **true** (слово «перевод» в `BUREAU_TOPIC_PATTERN_CI:1276`) |
| `shouldUseGeneralKnowledgeFallback` | **false** — есть «перевод», но нет ни одного глагола из `как\|где\|можн\|нужн\|…` (`:1291-1298`) |
| Охват базы | rules **398**, qa **202**, chunks **139** |

**Должен отвечать:** только внутренние документы (цена — коммерческий факт).
**Фактически:** сценария «перевод» в таксономии нет → LLM-классификатор почти наверняка вернёт `out_of_scope` → `isBureauTopic = true` → **открытый поиск по всей базе** (`:564-569`). Ответ строится из 4 прайсов (`Прайс на перевод и заверение-010126` — 199 правил, `…Наливайко М В 01012026` — 80 правил и др.).
**Защита от выдумывания цены:** `shouldUseGeneralKnowledgeFallback = false`, поэтому даже при провале поиска в общие знания вопрос **не уйдёт** — вернётся «в базе знаний нет данных» (`:908-909`). Это правильно и работает.
**Риск:** прайсов **четыре** (клиентский/внутренний апостиль, два прайса на перевод), между ними нет приоритета — см. §4.

### 3.3. «график работы Минюста в пятницу»

| Проверка | Результат |
|---|---|
| Канонический Q&A-оверрайд | overlap **0.000** → мимо |
| Детерминированный гейт | **не сработал**. `mentionsApostille = false` (слова «апостиль» нет!), поэтому ветка `mentionsApostille && mentionsMinJustice` (`:263`) **не достигается** → LLM-классификатор |
| Guardrail | нет |
| `shouldUseGeneralKnowledgeFallback` | **false** (нет «апостил/нотари/…» и практического глагола) |
| Охват базы | rules **114**, qa **42**, chunks **84** |
| Наличие расписаний в базе | «график/часы/режим работы»: **4** ACTIVE-правила, **1** Q&A, **3** чанка |

**Должен отвечать:** только внутренние документы (график ведомства — изменяемый факт).
**Фактически:** упоминание Минюста без слова «апостиль» **проваливает детерминированную маршрутизацию** — решение отдаётся LLM-классификатору, который, скорее всего, вернёт `out_of_scope` → открытый поиск.
**Главный риск здесь:** расписаний в базе почти нет (4 правила на всю базу), а `HallucinationLog` содержит 134 записи и 224 неподтверждённых утверждения — и именно «выдуманное расписание» названо в комментарии кода классом галлюцинации, ради которого гейт и написан (`:923-924`: «Вторник-пятница 10-17»). Consistency-gate это ловит и регенерирует (все 134 записи `regenerated=true`), но ловит **после** генерации, а не предотвращает.

### 3.4. «где получить повторное свидетельство о рождении»

| Проверка | Результат |
|---|---|
| Канонический Q&A-оверрайд | overlap **0.000** → мимо |
| Детерминированный гейт | **не сработал** (нет «апостиль») → LLM-классификатор |
| `isBureauTopic` | **true** («свидетельств») |
| `shouldUseGeneralKnowledgeFallback` | **true** («свидетельств» + «где») |
| Охват базы по «повторное/восстановление/дубликат свидетельства» | rules **0**, qa **0**, chunks **0** |

**Должен отвечать:** общие знания (это процедура ЗАГС/Госуслуг, не услуга бюро).
**Фактически:** ровно так и происходит — база пуста → `confidenceLevel = insufficient` → `general_ai` (`:876`). **Вывод:** единственный из четырёх примеров, где маршрутизация работает точно по замыслу владельца продукта.

### 4.2. Домены как источник приоритета отключены сознательно

Комментарий `:694-700`: аудит 23.04.2026 показал, что `notary/legal_compliance/pricing/general_ops` покрывают 161 из 163 правил. Данные прода подтверждают, что стало только хуже: `pricing` — **1487** правил из 1723 ACTIVE (86%), `legal_compliance` — 1166, `notary` — 1038, `sales_clients` — 1016. Средне 4.5 домена на правило (7683 связи / 1723). Домены сигнала не несут; 7683 + 2605 + 854 связей — мёртвый вес.

### 4.3. Где разрешения конфликта нет вообще

**Один факт живёт в 3-4 местах одновременно.** Пересечения по проду:

| Факт | ACTIVE `Rule` | ACTIVE `QAPair` | `DocChunk` |
|---|---:|---:|---:|
| цена / стоимость / тариф | **424** | 103 | 65 |
| срок | 173 | 63 | 74 |
| апостиль | 466 | 176 | 82 |
| адрес / офис / метро | 63 | 24 | 51 |
| нотариус | 54 | 20 | 34 |
| график / часы / режим работы | 19 | 5 | 7 |

Что происходит при расхождении:

1. **Все источники подаются модели как равнозначные** (`:179`). Если правило говорит «2500₽», а чанк из другого прайса — «3000₽», выбор делает LLM без всяких критериев. Промпт лишь запрещает *смешивать* цитаты (п.4, `:161`), но не говорит, **какой** выбрать.
2. **Нет приоритета по свежести.** Ранжирование правил — по `confidence` и текстовому совпадению (`:729`, `:746-752`), не по `updatedAt`. Клиентский прайс от 010126 и внутренний от 010125 конкурируют на равных.
3. **Механизм версионирования не используется для разрешения конфликтов.** `supersedesRuleId` / `supersedesQaId` в схеме есть, 238 правил SUPERSEDED и 70 Q&A SUPERSEDED — но фильтр в поиске просто `status: 'ACTIVE'`; цепочка версий при синтезе не читается.
4. **`detectRuleConflicts` (`src/lib/ai/rule-conflict-detector.ts:71`) не импортируется ни одним модулем.** Мёртвый код. `AIQuestion.issueType = 'price_conflict'` предусмотрен схемой (`schema.prisma:357`), но в проде таких записей 0.
5. **`LibrarianEntry.verificationStatus` c уровнем `CANONICAL`** (`schema.prisma:588-593`) — готовый механизм «единственного источника правды» — не заполнен (0 строк) и движком ответов не читается.

### 4.4. Что consistency-gate закрывает, а что нет

`verifyAnswer` (`consistency-gate.ts:66`) сравнивает утверждения ответа с **объединением** чанков + правил + Q&A (`:940-944`). Он ловит факт, которого нет **ни в одном** источнике. Он **не** ловит противоречие **между** источниками: если два прайса дают разные цены, любая из них «подтверждена», и гейт пропускает.

Комментарий `:936-939` фиксирует и обратный риск: проверка только по чанкам ложно помечала факты из правил как галлюцинации, а регенерация **стирала верный факт**.

Прод: 134 срабатывания, 224 неподтверждённых утверждения, **100% привели к регенерации**. По сценариям: `null` (открытый поиск) 67, `apostille.min_justice` 51, `apostille.zags.lo` 12, `apostille.zags.spb` 4. Половина проблем — в открытом поиске, т.е. там, где сценарного сужения нет.

### 4.5. Скрытые дефекты приоритизации

1. **Окно в 200 записей у канонического оверрайда.** `findCanonicalQaOverride` (`:426-430`) берёт `take: 200, orderBy: createdAt desc`, и **только потом** фильтрует по authority-тегу. Сейчас все 5 авторитетных пар созданы 17-18.07 (самые свежие) и в окно попадают. Как только добавят 200 новых обычных Q&A, авторитетные **молча выпадут** из окна и оверрайд перестанет работать. Фильтр по тегу нужно делать в SQL, а не в памяти.
2. **`scenarioKey = 'capability'` — ключ-сирота.** Все 5 авторитетных Q&A им помечены, но в `SCENARIOS` (`scenarios.ts:79-188`) такого узла нет. Фильтр `scenarioWhere` (`:702-704`) пропускает только `scenarioKey = null` или ключи из цепочки предков. Значит: при **любом** определённом сценарии (`scenario_clear`) эти 5 пар **исключены** из обычного поиска (шаг 7); они достижимы только через оверрайд (шаг 2) или открытый поиск (где фильтр пуст). Оверрайд это маскирует — до тех пор, пока сработает дефект №1.
3. **Лишний LLM-вызов.** `classifyScenario` (LLM) выполняется на `:518`, а его результат может быть полностью отброшен оверрайдом на `:531-535`. Порядок обратный оптимальному: дешёвая проверка оверрайда должна идти первой.
4. **`answerSource` не персистится.** Оба места записи ассистентских сообщений — `src/app/api/ask/route.ts:120-130` и `src/app/api/telegram/mini-app/route.ts:886-896` — пишут `confidence`, `confidenceLevel`, `domainsUsed`, `citationCount`, но **не `answerSource`**. Подтверждение по проду: 0 из 849 сообщений содержат этот ключ; в метаданных встречаются только `confidence` (849), `confidenceLevel` (846), `domainsUsed`/`citationCount` (824), `queryAnalysis`/`needsClarification` (728), `scenarioKey` (34), `scenarioClarification` (30). **Это и есть прямая причина жалобы «я не понимаю, на что бот смотрит»** — данных для ответа на этот вопрос в системе просто не сохраняется. Поле есть в UI плейграунда (`playground/page.tsx:386`) и в эскалациях (`ai-escalation.ts:167`), но не в истории.

## Приложение: как воспроизвести цифры

Все числа получены запросами `SELECT`/`groupBy` к проду через `railway run node <script>` из `C:\dev\translation` (Railway CLI, проект слинкован). Временные скрипты удалены после снятия среза. Ключевые проверки:

```sql
-- авторитетные Q&A
SELECT metadata->>'authorityTag', count(*) FROM "QAPair" WHERE metadata IS NOT NULL GROUP BY 1;

SELECT "sourceSpan"->>'authorityTag', count(*) FROM "Rule" WHERE "sourceSpan" IS NOT NULL GROUP BY 1;
-- источник ответа в истории (ключа нет ни в одной строке)
SELECT metadata->>'answerSource', count(*) FROM "ChatMessage" WHERE role='ASSISTANT' AND metadata IS NOT NULL GROUP BY 1;
-- pgvector
SELECT extname FROM pg_extension;
```
