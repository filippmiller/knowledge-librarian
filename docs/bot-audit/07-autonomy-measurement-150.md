# Замер автономности на 150 реальных вопросах

**Дата:** 2026-07-31
**Скрипт:** `scripts/measure-autonomy-150.ts`
**Сырые данные:** `docs/bot-audit/.autonomy-150-results*.jsonl` (150 строк, по одной на вопрос)
**Предыдущие замеры:** `out-of-corpus-rephrased.md` (15 вопросов), `out-of-corpus-after-containment.md` (15 вопросов)
**Состояние кода:** 145 вопросов измерены до коммита `2de268c`, 5 — после. См. §10 — это важная оговорка, читать до выводов.

---

## Короткий ответ владельцу

**Нет, в 2% мы не укладываемся, и это не шум.**

Из 94 ответов, которые ушли бы клиенту автоматически, **7 содержат ошибку по
вашему определению** — противоречие фактам, а не неполнота. Это 7,4%.

95%-й доверительный интервал для этой доли — **от 3,0% до 14,7%**. Нижняя
граница выше цели, то есть цифра «мы уже около 2%» отвергается измерением, а не
просто «не подтверждается». Даже при самом мягком прочтении (если исключить один
спорный случай, см. §6) интервал — от 2,4% до 13,4%, и он всё равно целиком выше
2%.

Чтобы **доказать** порог 2%, нужен прогон, где на ~150 отправленных ответов не
будет ни одной ошибки: 0 из 150 даёт верхнюю границу ровно 2,0%. Сегодня мы от
этого далеко.

Автономность при этом высокая: **64% вопросов ушли бы клиенту без человека**.
То есть система не осторожничает — она отвечает много и ошибается вместе с этим.

## 1. Что именно измерялось

Взят корпус `docs/email-bot/may2026-knowledge-base-final.json` — 180 кейсов из
переписки Bitrix за май 2026, где поле `answer` написано живым оператором.
Отобрано 150: пропорционально по `category`, внутри категории по убыванию
`freq`. Дубликатов вопросов в корпусе нет (180 уникальных из 180).

Каждый вопрос прогонялся **движком в процессе** (`answerQuestionEnhanced`,
аудитория `client`) на продовой базе через `railway run`, затем через
`resolveDelivery` — прод не задействован, измеряется рабочее дерево.

Ответ судился той же моделью и **тем же промптом судьи**, что и в прошлом замере
(скопирован дословно из `scripts/rerun-out-of-corpus-inprocess.ts`), где прямо
сказано: оператор — эталон по смыслу, но не по полноте, и отсутствие у бота
факта, названного оператором, само по себе не ошибка.

Судился только тот ответ, который реально ушёл бы клиенту (`delivery ===
'answer'`). Это принципиально: доля ошибок считается от **отправленных**, а не от
всех заданных.

## 2. Объём: честный учёт

| | |
|---|---|
| отобрано вопросов | **150** |
| строк результата записано | **150** |
| движок не ответил после 3 попыток | **4** |
| измерено | **146** |
| ушло бы клиенту (= прошло через судью) | **94** |
| судья не ответил | **0** |

**Потеряно на сбоях: 4 вопроса из 150 (2,7%).** Все четыре — обрыв соединения с
провайдером (`TypeError: terminated`), исчерпаны три повтора с паузами 8 и 16
секунд:

- №53 `requirement` — «Что нужно для истребования документов из-за рубежа и проставления апостиля по доверенности?»
- №130 `policy` — «Когда подписываются акты выполненных работ — до или после получения перевода?»
- №140 `policy` — «Можете удалить мои документы и письмо с персональными данными?»
- №148 `location` — «Можно ли забрать готовый заказ в другом офисе, не в том, где он готовится?»

Прошлый замер терял 8 из 15 (53%). Пауза 4000 мс и три повтора снизили потерю до
2,7%, но не до нуля. Потерянные вопросы не заменялись другими и в знаменателях
не участвуют.

**Оговорка о методе прогона.** Один вопрос стоит ~150 секунд, поэтому 150
вопросов шли шестью параллельными процессами по диапазонам. Диапазоны не
пересекались, значит **повторных замеров одного вопроса нет** и данных о
воспроизводимости этот прогон не даёт. Прошлый замер показал, что один и тот же
вопрос на одном и том же коде может дать разные решения о доставке, — этот эффект
здесь не измерен.

## 3. Автономность: сколько ушло бы клиенту

Из 146 измеренных:

| решение | сколько | доля от измеренных |
|---|---|---|
| `answer` — ушло бы клиенту автоматически | **94** | 64% |
| `escalate` — к человеку | 46 | 32% |

Почему удерживались 46:

- 33 — низкая или недостаточная уверенность (`low` / `insufficient`);

- 1 из них — ответ из общих знаний модели (`general_ai`), такие не отправляются никогда.

Источники отправленных ответов: 88 из базы знаний (`knowledge_base`), 6 из
детерминированных веток (`deterministic_guardrail`).

## 4. Ошибки среди отправленных

Судья по 94 отправленным: **OK 48, WEAK 37, WRONG 9**.

Каждый из 9 вердиктов WRONG перепроверен вручную. **Два отменены** — судья ошибся
(разбор в §6). Осталось **7 подтверждённых ошибок**.

| счёт | ошибок / отправлено | доля | 95% ДИ (двусторонний, Клоппер–Пирсон) | односторонняя верхняя граница |
|---|---|---|---|---|
| сырой вердикт судьи | 9 / 94 | 9,6% | 4,5% – 17,4% | 16,1% |
| **после ручной проверки** | **7 / 94** | **7,4%** | **3,0% – 14,7%** | 13,5% |
| без спорного №49 (§5) | 6 / 94 | 6,4% | 2,4% – 13,4% | 12,2% |

**Как это читать.** Точечная оценка 7,4% сама по себе ничего не доказывает —
доказывает интервал. Нижняя граница 3,0% означает: если бы истинная доля ошибок
была 2%, увидеть 7 ошибок на 94 отправленных было бы маловероятнее, чем 1 к 20.
Поэтому вывод «порог 2% не достигнут» — не осторожная формулировка, а результат.

Обратная задача, чтобы было с чем сравнивать в следующий раз:

| наблюдение | верхняя граница доли ошибок (95%) |
|---|---|
| 0 ошибок из 40 | 7,2% |
| 0 ошибок из 94 | 3,1% |
| 0 ошибок из 150 | 2,0% |
| 0 ошибок из 300 | 1,0% |

То есть даже идеальный прогон на 40 вопросах доказывает только «не хуже 7%».
Порог 2% требует **безошибочных 150 отправленных** — и это минимум, при первой
же ошибке планка отодвигается за 300.

## 5. Разбор каждой подтверждённой ошибки

### №20 · «Можно ли поставить апостиль на сам перевод?»
`answer` · 57% medium · источник: база знаний

**Бот:** «**Нет**, апостиль ставится только на оригинал документа или на
нотариальную копию, но не на сам перевод». Дальше в том же ответе описывает, как
нотариально заверенный перевод подаётся в Минюст на апостиль.

**Оператор:** «Да, бюро может проставить апостиль на перевод. Это отдельная
услуга со своим сроком (около 2 недель)».

**В чём противоречие:** прямое «нет» на вопрос об услуге, которую бюро оказывает.
Ответ вдобавок противоречит сам себе: первая фраза отрицает то, что описывают
следующие две. Клиент, прочитавший первую строку, уходит.

### №26 · «Предоставляете ли переводчика для присутствия в суде?»
`answer` · 90% medium · источник: **детерминированная ветка** · измерено на текущем коде (после `2de268c`)

**Бот:** «Для суда в России подойдёт один из двух вариантов: нотариальный перевод
либо перевод, заверенный подписью переводчика и штампом нашего бюро…»

**Оператор:** «Нет, услуги судебного переводчика (присутствие и устный перевод в
суде) компания не оказывает».

**В чём противоречие:** спросили про устного переводчика в заседание — бот
ответил про письменное заверение и ни словом не сказал, что услуги нет. Клиент
считывает это как «да, поможем».

**Корень:** в базе есть **правильная пара `CLIENT_SAFE`** с ответом слово в слово
как у оператора. Её перебила ветка про присяжный перевод
(`src/lib/ai/enhanced-answering-engine.ts`, ~строка 1749) — она срабатывает на
«суд» + «переводчик» и отвечает на другой вопрос. Детерминированная ветка
заглушила верный ответ базы.

### №37 · «Заверяете ли вы перевод, выполненный не у вас?»
`answer` · **100% high** · источник: база знаний

**Бот:** «Да, готовы заверить… только для документов второй или третьей
категории… **Стоимость услуги заверения составит 70% от стандартной цены
перевода**».

**Оператор:** «Заверить его отдельно нельзя — расчёт идёт по ставке перевода, то
есть документ переводится заново с нотариальным заверением».

**В чём противоречие:** разные коммерческие условия за одно и то же — 70% против
полной ставки, «можно» против «нельзя».

**Корень:** это не выдумка синтеза. В базе лежит пара `CLIENT_SAFE` «Заверяете ли
вы перевод, выполненный не у вас?» с ровно этим текстом про 70%. Ей же
противоречит внутреннее правило **R-1310**: «объяснить, что **не можем
подписаться под чужим переводом** и почему». То есть база противоречит сама себе,
а клиентская пара отдаётся с уверенностью 1.0 и без ручной проверки. **Самая
дорогая находка замера: ошибка в данных, а не в движке.**

### №49 · «Нужен ли оригинал документа для заверения и сшития перевода?» (спорный)
`answer` · 67% medium · источник: база знаний

**Бот:** «Если принимающая сторона не требует заверенного исходника, оригинал не
нужен… подшиваем перевод к простой ксерокопии… Для самого нотариального заверения
оригинал и не требуется».

**Оператор:** «Нотариальный перевод подшивается именно к оригиналу… Без оригинала
готовый перевод нельзя сшить и заверить».

**В чём противоречие:** прямое, по обязательности оригинала.

**Почему спорный:** ответ бота — это ровно та политика «трёх маршрутов
исходника», которую прошлая сессия установила намеренно (PR #29), сочтя
безусловное «нужен именно оригинал» ошибкой. Здесь операторский эталон мая 2026
противоречит установленной в июле политике. **Кто прав — вопрос владельца, а не
измерения.** В основной счёт (7 из 94) случай включён; строка «без спорного №49»
в таблице §4 показывает цену этого решения.

### №85 · «Как считается нотариальное заверение, если перевод на два языка подшивается к одному оригиналу?»
`answer` · 90% medium · источник: **детерминированная ветка**

**Бот:** «Зависит от того, куда вы подаёте документ, — вариантов три…» — и дальше
канонический текст про маршруты исходника.

**Оператор:** «Двуязычное заверение по стоимости считается как **два**
нотариальных заверения».

**В чём ошибка:** спросили про расчёт стоимости — бот ответил про подшивку. Про
удвоение цены не сказано ничего. Клиент получит счёт вдвое больше ожидаемого.

**Корень:** ветка «три маршрута исходника» срабатывает на слово «подшивается» и
перехватывает вопрос о цене.

### №103 · «Можно ли истребовать документ по скану доверенности, без оригинала?»
`answer` · 59% medium · источник: база знаний

**Бот:** «Да, по скану доверенности мы можем истребовать документ из ЗАГС. Это
работает, **если доверенность оформлена в России**».

**Оператор:** «Истребование по скану доверенности возможно, **если доверенность
оформлена в консульстве**. Для самого истребования в госоргане перевод должен
быть оригинальным (нотариально заверённым в бумаге), а не сканом».

**В чём противоречие:** условие названо противоположное. Заказ, принятый по этому
ответу, встанет в госоргане.

### №106 · «Как срочность влияет на стоимость перевода и заверения?»
`answer` · 65% medium · источник: база знаний

**Бот:** «Срочность влияет на стоимость заверения, **но не на стоимость самого
перевода**… Стоимость самого перевода зависит от языка и объёма, но не от
срочности».

**Оператор:** «Чем быстрее нужен готовый перевод, тем дороже: доступны разные
тарифы по срочности… Срочное выполнение делается с наценкой за срочность».

**В чём противоречие:** прямое отрицание существующей наценки. Цены заверения в
том же ответе (1100 / 1250 / 1300 / 1450 / 260 / 300 / 250) прайсу
соответствуют — ошибка ровно в одном утверждении, зато в самом коммерчески
чувствительном.

**Корень:** тарифы на перевод в таблицу сознательно не переносились, пока не
решена граница 2 и 3 категории. Пробел в данных превратился в уверенное «не
влияет».

## 6. Два вердикта судьи, которые я отменил

Судья ошибается в обе стороны, поэтому каждый WRONG перепроверен глазами.

### №12 · «Можно ли получить готовый перевод сканом / в цвете, без бумажного оригинала?» — **не ошибка**

Судья: бот «скрывает платность сканирования». Но бот нигде не сказал, что
сканирование бесплатно, — он о цене промолчал. По определению владельца это
неполнота, а не противоречие. Ответ **слабый** (половина вопроса — про цвет —
осталась без ответа, а фраза «Сканы отправляются после того, как вы внесёте
полную оплату заказа» создаёт впечатление, что скан входит в заказ), но ошибкой в
принятом смысле не является. Считаю WEAK.

### №89 · «Как заверить перевод иностранного документа с апостилем и проставить на него апостиль?» — **не ошибка**

Судья увидел противоречие в порядке действий: бот пишет «сначала на оригинал
проставляется апостиль (это делается в стране выдачи документа)», оператор
исходит из того, что апостиль на оригинале уже есть. Но утверждение бота само по
себе верно, а дальше он описывает **ту же** процедуру и **тот же** результат
(«два документа: оригинал с апостилем и нотариальная копия с переводом и
апостилем») — дословно как оператор. Лишний шаг, а не ложный факт. Считаю OK/WEAK.

**Прямое доказательство, что судья здесь не работает.** При перепроверке (§10) на
этот же вопрос бот дал ответ **без** шага «сначала апостиль на оригинал» — то
есть ровно тот порядок, отсутствие которого судья в первый раз назвал
противоречием. Судья снова поставил WRONG, с обратной формулировкой:

> первый прогон: «бот предлагает сначала апостилировать оригинал… это противоречие»
> перепроверка: «бот предлагает сначала копировать оригинал, потом искать апостиль… это ошибка в алгоритме»

Один и тот же судья забраковал оба взаимоисключающих порядка. Вердикту по этому
вопросу верить нельзя ни в какую сторону.

Если бы эти два вердикта не проверялись, отчёт назвал бы 9,6% вместо 7,4%.

- Больше половины отправленных ответов — WEAK (37 из 94). Неполнота ошибкой не

  запас, из которого при следующем изменении промпта возьмутся новые WRONG.

## 8. Проверка цен (`checkCertificationPriceAttribution`): сработала один раз, и это ложная тревога

Прошлый хендофф отмечал: «блокировка по цене на проде ни разу не наблюдалась».
Теперь наблюдалась.

Из 146 измеренных ответов проверка объявила противоречие **ровно один раз** —
вопрос №112 «Как считается стоимость нотариальной копии или тождественности
многостраничного документа?».

Ответ бота содержал верные цены: заверение копии 260 ₽/стр, тождественность
300 ₽/стр — обе совпадают с прайсом. Проверка споткнулась о последнюю фразу:

> «Разница в цене: тождественность дороже **на 40 рублей** за страницу.»

Связывание «цена относится к ближайшей услуге левее» приписало 40 ₽ услуге
«нотариальное заверение тождественности» и объявило противоречие с 300 ₽. Ответ
ушёл в `escalate` с `requiresHumanReview=true`.

**Итог: одно срабатывание на 146 ответов, и оно ложное.** Цена — один правильный
ответ, удержанный от клиента. Не катастрофа (молчание дешевле неверной цены,
как и задумано), но утверждение «ложных тревог ноль», основанное на 241
историческом ответе, этим прогоном опровергнуто: разностные конструкции («дороже
на N рублей», «дешевле на N») в корпусе аудита не встречались, а в живой
генерации встречаются.

Обратная сторона важнее: **ни одна из семи подтверждённых ошибок не была ошибкой
в цене заверения**. Проверка, ради которой делалась прошлая сессия, не поймала
ничего из того, что реально пошло не так, — потому что реальные ошибки лежат в
условиях услуги, а не в цифрах прайса.

## 9. Детерминированные ветки — худший источник в замере

| источник ответа | отправлено | OK | WEAK | WRONG |
|---|---|---|---|---|
| `knowledge_base` | 88 | 48 | 33 | 7 |
| `deterministic_guardrail` | 6 | **0** | 4 | **2** |

Шесть срабатываний детерминированных веток — **ни одного OK**. Все шесть:

| № | вопрос | вердикт |
|---|---|---|
| 26 | Предоставляете ли переводчика для присутствия в суде? | WRONG |
| 48 | К чему подшивается нотариальный перевод? | WEAK |
| 60 | Что нужно для заверения перевода штампами компании и нужен ли оригинал? | WEAK |
| 68 | К чему подшивается готовый нотариальный перевод? | WEAK |
| 85 | Как считается заверение, если перевод на два языка подшивается к одному оригиналу? | WRONG |
| 95 | Сколько ждать нотариальное заверение после того, как привезли оригиналы? | WEAK |

Пять из шести получили **один и тот же текст** про три маршрута исходника,
включая вопрос о стоимости (№85) и вопрос о сроке ожидания (№95). Ветка ловит
слово «подшивается»/«заверение» и отвечает заготовкой независимо от того, о чём
спросили.

Замысел прошлой сессии был верен: шесть формулировок одного вопроса перестали
давать четыре разных набора маршрутов. Но цена оказалась в том, что ветка теперь
отвечает и на соседние вопросы, у которых другой предмет. На выборке в 6
наблюдений это не приговор — но это **единственный источник в замере, где нет ни
одного хорошего ответа**, и оба его WRONG — перехваты чужого вопроса, а не
неверные факты внутри своей темы.

## 10. Оговорка о версии кода и точечная перепроверка

Во время прогона в `master` влилась чужая работа: коммит **`2de268c`** (PR #32,
«присяжного перевода в России нет») в 09:36 изменил
`src/lib/ai/enhanced-answering-engine.ts`, `src/lib/knowledge/source-document-route.ts`
и добавил `src/lib/knowledge/sworn-translation.ts`. Движок загружается в память
при старте процесса, поэтому каждый воркер работал на том состоянии `src/`,
которое застал:

| воркер | вопросы | старт | код |
|---|---|---|---|
| A | 1–25 | 08:36 | до `2de268c` |
| b, c, d, e | 31–150 | 08:52 | до `2de268c` |
| f | 26–30 | 09:45 | **после** `2de268c` |

Итого **145 вопросов из 150 измерены на коде, которого в `master` уже нет.**
Цифра 7,4% описывает состояние на утро 31 июля, а не текущий `HEAD` (`1d93110`).
Это дефект моего замера: надо было зафиксировать коммит перед стартом.

### Что показала перепроверка на текущем дереве

Двенадцать вопросов — семь подтверждённых ошибок и пять срабатываний
детерминированной ветки — переспрошены заново на `HEAD 1d93110`
(`ONLY=… railway run npx tsx scripts/measure-autonomy-150.ts`):

| № | было | стало | что это значит |
|---|---|---|---|
| 37 | WRONG | **WRONG**, 100% high | ошибка в паре базы жива, отдаётся с уверенностью 1.0 |
| 49 | WRONG | **WRONG** | расхождение политики трёх маршрутов с оператором живо |
| 103 | WRONG | **WRONG** | «доверенность оформлена в России» звучит по-прежнему |
| 20 | WRONG | WEAK | плоское «нет» ушло, ответ стал «апостиль можно поставить и на перевод» |
| 85 | WRONG | WEAK | ветка **по-прежнему** перехватывает ценовой вопрос и отвечает про подшивку; смягчился только вердикт судьи |
| 106 | WRONG | **не отправлен** (`escalate`) | ответ исправился («добавляется наценка за срочность») и всё равно удержан |
| 12, 89 | WRONG (отменены мной) | WEAK / WRONG | подтверждают §6: №12 действительно WEAK, №89 судья разворачивает на 180° |
| 48, 60, 68, 95 | WEAK | WEAK | без изменений |

**Как это читать.** Двенадцать наблюдений не дают новой доли и не отменяют
измеренную. Разница между «WRONG» и «WEAK» на одном прогоне лежит в пределах
разброса, который уже фиксировался в прошлом замере. Достоверно можно сказать
только одно: **три ошибки из семи воспроизводятся на текущем коде дословно**, и
среди них — обе самые дорогие (№37 с уверенностью 1.0 и №103 с обратным
условием). Перехват ценового вопроса детерминированной веткой (§9) тоже
воспроизводится, хотя коммит `2de268c` заявлял его исправление: «сколько стоит
нотариальный перевод по скану» вылечили, а «как считается заверение, если перевод
на два языка подшивается» — нет.

## 11. Что из этого следует

Порядок — по стоимости ошибки, а не по трудоёмкости.

1. **Противоречие в базе про заверение чужого перевода (№37).** Пара
   `CLIENT_SAFE` обещает 70% от цены перевода, внутреннее правило R-1310 говорит
   «не можем подписаться под чужим переводом», оператор в мае говорил «нельзя,
   считается по ставке перевода». Отдаётся клиенту с уверенностью 1.0. Нужно
   решение владельца, какая версия верна, и правка данных.
2. **Сузить условия срабатывания детерминированных веток.** Ветка про присяжный
   перевод не должна перехватывать вопрос об устном переводчике в суде (в базе
   уже есть верный ответ). Ветка про маршруты исходника не должна отвечать на
   вопросы о цене и сроке.
3. **Истребование по скану доверенности (№103)** — условие названо
   противоположное операторскому (Россия против консульства). Воспроизводится на
   текущем коде.
4. **Апостиль на перевод (№20)** и **срочность против цены перевода (№106)** —
   на перепроверке оба ответа выправились сами. Проверять не срочно, но нельзя
   считать закрытым: изменение пришло не от адресной правки, а вместе с чужим
   коммитом, и держится на одном наблюдении.
5. **Ложная тревога проверки цен на разностных конструкциях** — «дороже на N
   рублей» не является приписыванием цены услуге.
6. **Фиксировать коммит перед замером.** Мой прогон измерил код, которого в
   `master` уже нет, потому что параллельная сессия влила правки в середине.
   Скрипт должен писать `git rev-parse HEAD` в файл результатов и отказываться
   стартовать при грязном дереве.
7. **Повторить замер после правок на тех же 150 вопросах.** Скрипт
   возобновляемый, сравнение будет прямым.

**Чего этот замер НЕ показал:** воспроизводимости (диапазоны воркеров не
пересекались, каждый вопрос задан один раз), поведения на формулировках, не
попавших в корпус, и состояния текущего `master` (145 из 150 вопросов измерены до
`2de268c`). Все три оговорки означают, что 7,4% — оценка по одному прогону одной
выборки на одном состоянии кода, а не константа системы.

## Приложение: как воспроизвести

```bash
# полный прогон одним процессом (~6 часов)
railway run npx tsx scripts/measure-autonomy-150.ts

# параллельно диапазонами (~1,5 часа), каждый со своим файлом результатов
FRESH=1 RANGE=1-30    SUFFIX=.a railway run npx tsx scripts/measure-autonomy-150.ts &
FRESH=1 RANGE=31-60   SUFFIX=.b railway run npx tsx scripts/measure-autonomy-150.ts &
FRESH=1 RANGE=61-90   SUFFIX=.c railway run npx tsx scripts/measure-autonomy-150.ts &
FRESH=1 RANGE=91-120  SUFFIX=.d railway run npx tsx scripts/measure-autonomy-150.ts &
FRESH=1 RANGE=121-150 SUFFIX=.e railway run npx tsx scripts/measure-autonomy-150.ts &

# смоук на трёх вопросах
FRESH=1 LIMIT=3 railway run npx tsx scripts/measure-autonomy-150.ts

# точечная перепроверка конкретных номеров после правок
FRESH=1 ONLY=20,37,49,85,103,106 SUFFIX=.r1 railway run npx tsx scripts/measure-autonomy-150.ts
```

Прогон возобновляемый: уже измеренные номера читаются из своего
`.autonomy-150-results*.jsonl` и не переспрашиваются. Без `FRESH=1` файл не
обнуляется.
