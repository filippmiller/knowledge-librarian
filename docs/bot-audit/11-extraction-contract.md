## 1. Правильно ли мы задаём вопросы

### 1.1 Что происходит физически

Процессор — `src/app/api/documents/[id]/process-stream/route.ts`. Три фазы:

1. **DOMAIN_CLASSIFICATION** — `src/lib/ai/domain-steward-stream.ts`
2. **KNOWLEDGE_EXTRACTION** — `src/lib/ai/knowledge-extractor-stream.ts`
3. **CHUNKING** — `src/lib/ai/chunker.ts`

Третья фаза **не содержит модели вообще**: `splitTextIntoChunks()`
(`chunker.ts:34-96`) режет `rawText` на куски по 1000 символов с перекрытием
200 (`chunker.ts:4-5`), с попыткой сдвинуть границу к `\n\n`, `.\n`, `. `, `\n`
(`chunker.ts:50`). Никакого понимания структуры (таблица, список, раздел) нет.
В `route.ts:640-644` «промпт» фазы чанкинга — это литеральная строка
`Размер чанка: 1000 символов\nПерекрытие: 200 символов`.

### 1.2 Фаза 1 — классификация домена, дословно

`domain-steward-stream.ts:27-56`, системный промпт:

> Ты - Хранитель доменов библиотеки знаний бюро переводов.
> Твоя задача - классифицировать документы по подходящим доменам знаний и
> предлагать новые домены при необходимости.
> […]
> 1. Ты НИКОГДА не создаёшь домены самостоятельно - ты только ПРЕДЛАГАЕШЬ и ОБЪЯСНЯЕШЬ
> 2. Для каждой классификации указывай чёткую причину
> 3. При неуверенности добавляй вопрос для администратора
> 4. Используй точечную нотацию для иерархических доменов (например, "notary.veremiy_msk")
> 5. Уверенность должна отражать твою реальную оценку (от 0.0 до 1.0)

Просимая схема (`domain-steward-stream.ts:115-135`): `documentDomains[]`
(`primaryDomainSlug`, `secondaryDomainSlugs[]`, `confidence`, `reason`),
`newDomainSuggestions[]`, `questionsForHuman[]`.

**Дефект №1 фазы 1:** модель видит `documentText.slice(0, 8000)`
(`domain-steward-stream.ts:112`). Для «Публичная оферта» (15913 симв.) и
«Прайс на перевод и заверение-010126» (15071 симв.) классификатор не видит
больше половины документа. Замерено: `rawText` длины по документам —
`scripts/audit-extraction-contract-2.ts`.

**Дефект №2 фазы 1:** промпт не ограничивает число вторичных доменов и не даёт
критерия «когда домен НЕ ставить». Результат — раздел 2.3.

### 1.3 Фаза 2 — извлечение знаний, дословно

`knowledge-extractor-stream.ts:34-125`. Полный системный промпт (сокращения мои
только в разметке заголовков, текст дословный):

> Ты - Экстрактор знаний для бюро переводов "Аврора".
> ВСЕ ТЕКСТЫ ТОЛЬКО НА РУССКОМ ЯЗЫКЕ.
> **ГЛАВНАЯ ЗАДАЧА: извлечь МАКСИМАЛЬНОЕ количество конкретных правил из текста.
> Лучше извлечь 30 правил, чем пропустить 20 из-за неуверенности.**
>
> ═══ ЧТО СЧИТАЕТСЯ ПРАВИЛОМ ═══
> Каждое из следующего = ОТДЕЛЬНОЕ правило:
> • Любая цена, тариф, стоимость — НО если это ячейка тарифной таблицы (строка=язык/услуга, столбец=срок), то см. раздел ПРАЙС-ЛИСТЫ ниже
> • Любой срок выполнения или действия документа
> • Любое требование к документу (формат, заверение, апостиль, нотариус)
> • Любая процедура или последовательность шагов
> • Любое контактное лицо или ответственный
> • Любая скидка, наценка, коэффициент, надбавка
> • Любое ограничение, условие или исключение
> • Любой тип услуги с описанием
> • Любое правило работы с клиентом
> • Отраслевые аббревиатуры, НЕ очевидные новому сотруднику (СОН, НЗКО, РВПО, ТПП, ПЕМТ и т.д.)
>
> ═══ КАК ПИСАТЬ ПРАВИЛА ═══
> title (5–12 слов) […]
> body (полное описание):
>   - Конкретные числа, суммы, даты — без округлений
>   - Если есть условия — перечисли все
>   - Если это процедура — пронумеруй шаги
>   - Если есть исключения — укажи явно
>   […]
> confidence:
>   0.95–1.0 — конкретная цифра прямо в тексте
>   0.80–0.94 — вывод из контекста с высокой уверенностью
>   0.60–0.79 — неточно или требует уточнения
> sourceSpan.quote: дословная цитата из документа (макс. 150 символов)
> sourceSpan.locationHint: раздел или заголовок, где встретилось
>
> ═══ ПРАЙС-ЛИСТЫ И ТАРИФНЫЕ ТАБЛИЦЫ (ОБЯЗАТЕЛЬНО) ═══
> ⚠ КРИТИЧЕСКОЕ ПРАВИЛО: если в тексте есть таблица с ценами, где строки = языки/услуги,
> а столбцы = сроки […]
> ЗАПРЕЩЕНО: создавать по 1 правилу на каждую ячейку […]
> ОБЯЗАТЕЛЬНО: создать ОДНО правило на один язык, включив ВСЕ сроки в body
> […]
> Итог: таблица из 24 языков → 24 правила (не 120 и не 240).
>
> ═══ ДЕДУПЛИКАЦИЯ ═══ […]
> ═══ НЕЯСНОСТИ ═══
> Отмечай только реально неоднозначное:
> - "примерно", "около", "как правило" без точных цифр
> - Устаревшие данные (упоминание прошлых лет)
> - Противоречия между разными частями текста
>
> Коды правил: R-1, R-2, R-3 ... (строго последовательно)

Пользовательское сообщение (`knowledge-extractor-stream.ts:240-277`) задаёт
схему ответа:

```json
{ "rules": [ { "ruleCode", "title", "body", "confidence",
               "sourceSpan": { "quote", "locationHint" } } ],
  "qaPairs": [ { "question", "answer", "linkedRuleCode" } ],
  "uncertainties": [ { "type", "description", "suggestedQuestion" } ] }
```

**Это весь контракт. Всё, что модель обязана вернуть на правило, — пять полей:
код, заголовок, тело, самооценка уверенности и цитата с текстовой подсказкой
о месте.**

### 1.4 Оценка против того, что нужно

| Требуется | Есть в контракте? | Факт |
|---|---|---|
| **Область действия** (услуга / орган / регион / тип документа / тип клиента) | **Нет** | В промпте нет ни слова «область», «сценарий», «для какой услуги». Поля в схеме нет. `scenarioKey` в `commit.ts` не пишется вообще — `prisma.rule.create` (`commit.ts:208-217`) передаёт только `documentId, ruleCode, title, body, confidence, sourceSpan` |
| **Дата / версия источника** | **Нет** | Год упоминается только в разделе «НЕЯСНОСТИ» как повод для `uncertainty`. Поля нет. Замерено: год `20xx` встречается в теле лишь **31** активного правила из 1724 (1,8 %). При этом заголовок главного прайса — «Прайс-лист на услуги с 01.01.2026» — лежит в ячейке таблицы и в правила как дата действия не попадает |
| **Различение факт о мире / внутренняя процедура / цена** | **Нет** | Промпт перечисляет типы в разделе «что считается правилом» (строки 44–54), но в выходной схеме поля `type` нет. Все 1724 правила лежат в одной плоской таблице без типа |
| **Условие отдельно от утверждения** | **Нет** | Промпт говорит «Если есть условия — перечисли все» — то есть внутрь прозаического `body`. Отдельного поля нет. Замерено: «если» внутри `body` — **210** активных правил (12 %); это условия, которые ретривер не может ни отфильтровать, ни проверить |
| **Аудитория (клиент/внутреннее)** | **Нет** | Ставится вручную на уровне документа (`setDocumentAudience`, `audience.ts:35-46`) и каскадом переписывает правила. Модель об аудитории не спрашивается |

**Дополнительно найдено в промпте.**

- **Инструкция «лучше извлечь 30, чем пропустить 20»** (строка 39) прямо
  оптимизирует полноту против точности. Это и даёт 1724 активных правила
  на 44 документа общим объёмом 174 593 символа `rawText` — одно «правило»
  на ~101 символ исходника.
- **Устаревший few-shot с ценой.** Пример в промпте (`knowledge-extractor-stream.ts:101`)
  задаёт `"стандарт: 630 руб (с НЗ 1540 руб)"`. В действующем прайсе
  (`Прайс на перевод и заверение-010126`, таблица 2) строка английского —
  `АНГЛИЙСКИЙ 440 1540 530 1630 640 1740 770 2020 930 2180`. То есть промпт
  подсказывает модели конкретное число `630`, которого в текущем прайсе на этом
  месте нет. Проверено скриптом `audit-price-docx-demo.ts`.
- **`confidence` — самооценка, и она вырождена.** Замерено по проду:
  0,95 ровно — **1279** правил, ≥ 0,95 — **1641** из 1724 (95,2 %), < 0,8 — **8**.
  При этом `confidence` используется как основной ключ выборки при ответе:
  `orderBy: { confidence: 'desc' }, take: 100` (`enhanced-answering-engine.ts:1036-1041`)
  и как буст ранжирования (`:1052`). Отбор «топ-100 по уверенности» из 1641
  правила с одинаковым значением — это произвольный срез, порядок в нём
  определяется планировщиком Postgres.
- **Батчинг рвёт таблицы.** `BATCH_SIZE = 4500`, `BATCH_OVERLAP = 600`
  (`knowledge-extractor-stream.ts:156-157`). Для главного прайса (15071 симв.)
  это 4 батча. Замерено (`audit-price-batching.ts`):

  | батч | диапазон | токенов-заголовков (`КАТЕГОРИЯ`/`СТАНДАРТ`/`вкл. НЗ`) | строк-«голых чисел» |
  |---|---|---|---|
  | 1 | 0–4500 | 11 | 535 |
  | 2 | 3900–8400 | 6 | 529 |
  | 3 | 7800–12300 | 3 | 547 |
  | 4 | 11700–15071 | **0** | 38 |

  Четвёртый батч получает фрагмент прайса, в котором **нет ни одной строки
  заголовка**: модели предъявлены числа без указания, какой это срок и
  включено ли нотариальное заверение. В батчах 1–3 на 500+ осиротевших чисел
  приходится 3–11 заголовочных токенов.

### Вердикт по разделу 1

Вопросы задаются **неправильно по составу**: контракт из пяти полей физически
не может выразить область действия, условие и дату, а фаза чанкинга и вовсе
работает без модели и без понимания структуры. Плюс два усиливающих дефекта:
классификатор видит первые 8000 символов, а извлечение режет таблицы на батчи,
теряя заголовки колонок.

## 2. Правильно ли классифицируем

### 2.1 Аудитория

`src/lib/knowledge/audience.ts`. Значение хранится на `Document.audience`
(`schema.prisma:46`) и каскадом копируется в `Rule` / `QAPair` / `DocChunk`
одной транзакцией `setDocumentAudience()` (`audience.ts:35-46`), которая
вызывается в конце коммита (`commit.ts:350`).

Замерено:
- документы: 36 `INTERNAL_ONLY`, 8 `CLIENT_SAFE`;
- правила: 1418 `INTERNAL_ONLY`, 549 `CLIENT_SAFE`;
- **расхождений между `Rule.audience` и `Document.audience` — 0**. Каскад работает.

Что здесь **сломано не технически, а логически:** аудитория — свойство
**документа целиком**. Один документ не может содержать одновременно
клиентскую цену и внутренний адрес подачи, хотя реальные инструкции именно
такие. Модель об аудитории не спрашивается ни разу; человек проставляет метку
на файл. `checkClientSafety()` (`audience.ts:183-199`) — это сигнализация на
выходе, а не классификация на входе.

### 2.2 Сценарий

`src/lib/knowledge/scenarios.ts` — таксономия из 6 узлов, все внутри
`apostille`. `src/lib/knowledge/scenario-classifier.ts` — гейт **на вопросе
пользователя**, не на документе.

**`scenarioKey` не проставляется в пайплайне вообще.** В `commit.ts:208-217`
поля нет. Единственный источник — `scripts/backfill-scenarios.ts`, который
классифицирует документы регулярками по имени файла (`backfill-scenarios.ts:38-45`)
и сам содержит комментарий: «For future uploads, classification will use an LLM
against the taxonomy's facets, not these regexes» — не реализовано.

Замерено по проду:

| Сущность | Без `scenarioKey` | Всего |
|---|---|---|
| Document | 39 | 44 |
| Rule | 1546 | 1967 |
| QAPair | 599 | 743 |
| DocChunk | 204 | 228 |

Распределение правил по сценариям: `apostille` — 28, `apostille.min_justice` — 161,
`apostille.zags.spb` — 142, `apostille.zags.lo` — 90, `null` — 1546.

Фильтр ретрива (`enhanced-answering-engine.ts:1000-1002`,
`vector-search.ts:124,198,303,372`) устроен как
`scenarioKey IS NULL OR scenarioKey IN (предки)`. То есть **1546 правил без
сценария проходят через любой сценарный фильтр**. Это и есть механизм
«правила про апостиль всплывают в ответах про посольство»: у них не записана
область действия, а `NULL` трактуется как «универсально».

### 2.3 Домены

Проверено самостоятельно, отчёт не принимался на веру.

Активных правил — 1724. Связей `RuleDomain` на активных правилах — 6621,
то есть **3,84 домена на правило** в среднем (в отчёте от 2026-04 было 4,5 —
цифра изменилась, вывод нет). Всего доменов — 11.

Покрытие активных правил доменами:

| slug | правил | доля от 1724 |
|---|---|---|
| `pricing` | 1326 | 76,9 % |
| `legal_compliance` | 928 | 53,8 % |
| `sales_clients` | 903 | 52,4 % |
| `notary` | 800 | 46,4 % |
| `translation_ops` | 701 | 40,7 % |
| `general_ops` | 630 | 36,5 % |
| `formatting_delivery` | 598 | 34,7 % |
| `sales_clients.crm_checklists` | 330 | 19,1 % |
| `legal_compliance.consular_legalization` | 316 | 18,3 % |
| `hr_internal` | 67 | 3,9 % |
| `it_tools` | 22 | 1,3 % |

Распределение числа доменов на правило: 6 доменов — 424 правила, 5 — 266,
4 — 274, 3 — 155, 2 — 589, 1 — 8, 0 — 8.

Причина механическая: домены назначаются **документу**, а затем в `commit.ts:221-227`
каждому правилу этого документа приписываются **все** домены документа
(`uniqueDomainIds`), с той же `confidence`. Правило не классифицируется —
оно наследует объединение меток файла.

**Домены при ответе не используются.** `enhanced-answering-engine.ts:925-931`
передаёт в поиск пустой массив: `[], // domains disabled — scenario filter does
the narrowing`. Комментарий на `:989-998` фиксирует, что фильтр по доменам
эквивалентен отсутствию фильтра. Таблицы `RuleDomain` (7683 строки),
`QADomain` (2605), `ChunkDomain` (854), `DocumentDomain` (133) — мёртвый вес:
они заполняются при коммите и не читаются при ответе.

### 2.4 Типизация правила

**Типа нет ни в схеме, ни в контракте.** В `model Rule` (`schema.prisma:174-212`)
нет поля типа. Значит и при ответе он использоваться не может.

Косвенный замер того, сколько типов сейчас свалено в одну таблицу (по активным
правилам): цена (`число + руб/₽`) — 371; условие (`если`) — 210; запрет
(`нельзя` / `запрещ` / `не приним`) — 34; исключение (`исключен` / `кроме`) — 20;
дата (`20xx`) — 31.

### Вердикт по разделу 2

Из четырёх осей классификации работает **одна**: аудитория (0 расхождений, но
гранулярность — документ, а не факт). Сценарий проставлен у 21 % правил и только
пост-фактум скриптом по имени файла. Домены проставлены у всех, несут ~3,8 метки
на правило и **отключены при ответе**. Типа правила не существует.

## 3. Правильно ли сохраняем и связываем

### 3.1 Что есть в схеме и что из этого живо

| Связь | Строка схемы | Используется при ответе? |
|---|---|---|
| `Rule.documentId → Document` | `schema.prisma:198` | Да — заголовок документа в цитатах (`enhanced-answering-engine.ts:1029,1461`) и провенанс (`:1453-1455`) |
| `Rule.supersedesRuleId` (версионирование) | `schema.prisma:199-200` | **Мертво.** Замерено: правил с `supersedesRuleId` — **0**, правил с `version > 1` — **0** |
| `QAPair.ruleId → Rule` | `schema.prisma:238` | Не читается при ответе: QA выбираются отдельным запросом (`enhanced-answering-engine.ts:1069-1089`) без `include: { rule }` |
| `QAPair.supersedesQaId` | `schema.prisma:239-240` | Частично: 70 QA в статусе `SUPERSEDED` |
| `RuleDomain` / `QADomain` / `ChunkDomain` / `DocumentDomain` | `schema.prisma:288-335` | **Мертво при ответе** (см. 2.3) |

### 3.2 Замеры по проду

**Объёмы.** Документов 44 (все `COMPLETED`). Правил 1967: `ACTIVE` 1724,
`SUPERSEDED` 238, `DEPRECATED` 5. QA-пар 743: `ACTIVE` 671, `SUPERSEDED` 70,
`DEPRECATED` 2. Чанков 228, все с эмбеддингом.

**Правила без документа.** 119 всего, **114 активных** (6,6 % активных).
Это ручные правила из Telegram/voice-контуров (`telegram/knowledge-manager.ts:108`,
`telegram/voice-handler.ts:82`, `voice-training/approve/route.ts:88`) и из
`scripts/fix-source-route-rules.ts:209`. Они **участвуют в выборке**
(`enhanced-answering-engine.ts:1027-1041` не фильтрует по `documentId`), но
**не могут быть процитированы**: провенанс отбрасывает их явно —
`.filter((r) => r.documentId != null && contextDocIds.has(r.documentId))`
(`:1453-1454`). Итог: правило может определить ответ и при этом не появиться
в списке источников.

**Дубли `ruleCode`.** Подтверждено ровно: **104 кода** имеют больше одной записи —
79 кодов по 3 записи и 25 кодов по 2. Максимум на один код — **3**.
Под дублирующимися кодами лежит 287 активных правил.
**Ни у одного из 104 кодов заголовки не совпадают** (`dup codes where ALL titles
identical = 0`; `dup codes with >1 distinct title = 104`). То есть это не копии,
а разные правила с одним именем. Пример `R-1379`:

| id | title | документ | audience |
|---|---|---|---|
| `cmq2btc62004e…` | Цена нотариального заверения в Москве | `cmppev8xa000i…` | INTERNAL_ONLY |
| `cmq2bwcyb0003…` | СОН — справка о несудимости, выдаваемая МВД | `cmppgtmq2002p…` | INTERNAL_ONLY |
| `cmq2bt6h5000p…` | Апостиль МЮ СПб стандартный срок и цена | `cmq264t310004…` | CLIENT_SAFE |

**Механизм коллизии установлен.** Стартовый номер берётся из **закоммиченных**
правил: `getExistingRuleCodesForStream()` возвращает коды только из таблицы
`Rule` со статусом `ACTIVE` (`knowledge-extractor-stream.ts:426-432`), а
`startCode = max + 1` (`route.ts:451-455`). Извлечение при этом пишет в
`StagedExtraction`, а не в `Rule`. Значит **любые два документа, обработанные
до коммита первого, получают один и тот же диапазон кодов**. Уникальности на
`ruleCode` в схеме нет (`schema.prisma:208` — обычный `@@index`, не `@@unique`),
`commit.ts:208` создаёт правило без проверки. При этом `ruleCode` — это то,
что показывается пользователю как ссылка на источник (`:1460`).

**Статусы и поиск.** 243 правила не `ACTIVE`. В поиске они **не участвуют**:
фильтр `status: 'ACTIVE'` стоит на всех точках выборки —
`answering-engine.ts:107,121`; `enhanced-answering-engine.ts:648,1028,1037,1073,1086`.
У `DocChunk` поля статуса нет вообще, поэтому чанки удалённых/устаревших правил
никак не помечаются.

**Остатки процесса.** `StagedExtraction` — 49 неубранных строк,
`AIQuestion` — 578, `DocumentRevision` — 3.

### 3.3 Можно ли по ответу дойти до строки исходного документа

**Нет.** Цепочка обрывается дважды.

*Обрыв 1 — цитата в ответе не является цитатой из документа.*
`enhanced-answering-engine.ts:1457-1467` строит блок «Источники» так:

```ts
quote: r.body.slice(0, 200) + (r.body.length > 200 ? '...' : ''),
```

То есть пользователю показывается **тело правила** (пересказ модели), а не
`sourceSpan.quote`. Дословная цитата, которую модель всё-таки вернула, в ответ
не попадает.

*Обрыв 2 — сама `sourceSpan` не содержит позиции.*
Замерено по 1724 активным правилам: ключи в `sourceSpan` — `quote` (1724),
`locationHint` (1723), плюс служебные `stagedRuleCode` / `committedFromStagedAt` /
`supersededRuleCodes` (472). Ключей `charOffset` — **0**, `chunkId` — **0**.
`locationHint` — свободный текст: **437 различных значений на 1724 правила**,
среди них «Раздел исключений», «Заголовок и контактные данные» — это не локатор.

*Насколько цитата хотя бы находится в документе.* Проверено программно:
из 1610 активных правил с документом у 1609 есть непустая цитата; после
нормализации (регистр, ё→е, кавычки, пробелы) **1378 цитат (85,6 %) найдены
в `Document.rawText` дословно, 231 (14,4 %) — не найдены**. Примеры ненайденных:

| Правило | Цитата |
|---|---|
| `R-1127` | `CRM разделена по типам сделок...` |
| `R-578` | `МЮ принимает: нотариальные копии` |
| `R-614` | `От лица заявителя. В любом отделении Сбербанка по квитанции (распечатать из данной папки)` |
| `R-616` | `От юр лица. Со счета юр лица на реквизиты КЗАГС` |

Часть из них — склейки нескольких ячеек таблицы, часть — сокращения с
многоточием. Для этих 231 правила исходную строку нельзя найти даже поиском
подстроки.

*Чанк знает позицию, но с правилом не связан.* `DocChunk.metadata` хранит
`{ startChar, endChar }` (`chunker.ts:69-72`), но связи `Rule → DocChunk` в
схеме нет, и `chunkId` в `sourceSpan` не пишется. Восстановить связь можно
только текстовым поиском — который проваливается на тех же 14,4 %.

*Качество-гейт проверяет не то.* `lintRule()` (`extraction-lint.ts:62-92`)
сравнивает числа из `body` с числами из **`sourceSpan.quote`**, а не из
документа. Если модель выдумала и число, и цитату — гейт молчит. Плюс он
не блокирующий (`commit.ts:232-245`) — предупреждения уходят в `AIQuestion`.

### Вердикт по разделу 3

Связывание сломано в самой чувствительной точке: **у знания нет проверяемого
адреса в источнике**. Идентификатор, который показывается как ссылка (`ruleCode`),
неуникален у 104 кодов; позиции в документе нет ни у одного правила; цитата,
показанная пользователю, — это пересказ модели; 14,4 % сохранённых цитат нельзя
найти в собственном документе; 6,6 % активных правил вообще не имеют документа
и при этом влияют на ответ, не появляясь в источниках.

## 5. Предлагаемый контракт извлечения

### 5.1 Принципы

1. **Один факт — одна запись.** Сейчас 211 активных правил содержат ≥ 10
   трёхзначных чисел (замерено): это упакованные строки прайса. Такую запись
   нельзя ни проверить, ни адресно исправить.
2. **Область действия обязательна.** Запись без области действия не должна
   попадать в базу. `NULL` не может означать «универсально» — универсальность
   должна утверждаться явно.
3. **Позиция в документе обязательна и проверяется программно.** Цитата с
   офсетами; если `rawText.slice(start, end)` не равен цитате — запись
   отклоняется до всякого LLM-судьи.
4. **Числа выносятся из прозы в структуру.** Иначе их нельзя сверить с
   прайсом и нельзя обновить при смене тарифа.
5. **Модель не назначает идентификаторы.** `ruleCode` присваивает база.
6. **Таблицы разбираются детерминированно, не моделью.**

            "description": "что нужно спросить у владельца, чтобы факт стал полным (нет даты, неясна область, противоречие)" }
        }
      }
    },

    "conflicts": {
      "type": "array",
      "description": "Пары фактов внутри документа с одинаковой областью и разными значениями.",
      "items": {
        "type": "object",
        "required": ["localIdA","localIdB","kind","detail"],
        "properties": {
          "localIdA": { "type": "string" },
          "localIdB": { "type": "string" },

### 5.3 Как этот контракт закрывает найденные ошибки

| Ошибка двух сессий | Что её делает невозможной |
|---|---|
| Правило про апостиль всплыло в ответе про посольство | `scope.appliesTo.service` + `scope.universality`; запись без области не коммитится, `NULL` больше не означает «универсально» |
| Один код — три разных правила | `localId` действует только внутри ответа; постоянный `ruleCode` присваивает база транзакционно; в схеме — `@@unique([ruleCode])` |
| Прайс «кашей» | Таблицы разбираются парсером, не моделью; `values[].tier` + `values[].includes` + `evidence.tableRef.colHeader` фиксируют колонку |
| Цитата, которой нет в документе | `charStart/charEnd` проверяются программно до коммита; 14,4 % нынешних записей такую проверку не прошли бы |
| Ответ нельзя проследить до строки | В цитировании показывается `evidence.quote` + `sectionPath`, а не пересказ; офсет ведёт в конкретное место |
| Устаревший прайс отвечает как действующий | `sourceDocument.effectiveFrom` / `supersedesDocumentId`; при конфликте побеждает документ с более поздней датой |
| Условие потеряно в прозе | `scope.conditions[]` — отдельный массив с собственными цитатами |
| «Уверенность» вырождена в 0,95 | `confidence.basis` ограничивает потолок: `inferred_from_context` не может дать > 0,8 |
| Внутренние сведения в клиентском ответе | `audience.proposed` + `reason` на КАЖДЫЙ факт, а не на файл целиком |

Сопутствующие изменения вне контракта модели (нужны, иначе контракт не спасёт):
`@@unique([ruleCode])` на `Rule`; связь `Rule → DocChunk` или хранение офсетов;
цитирование `evidence.quote` вместо `body`; отказ от `confidence` как ключа
сортировки при ретриве.

## 6. Как проверить качество переразбора ДО прогона всего корпуса

Прогонять 44 документа вслепую нельзя: прошлый раз это дало 1724 правила,
104 коллизии кодов и 231 непроверяемую цитату, и разбор занял две сессии.

### 6.1 Выбор трёх документов

Три документа покрывают три разных режима отказа:

| # | Документ | Почему он |
|---|---|---|
| 1 | `Прайс на перевод и заверение-010126` | 8 таблиц, 192 строки, 1816 ячеек — худший случай структуры; сейчас 199 правил |
| 2 | `Инструкция оформление Апостиля в МинЮсте` | чистая процедура + 2 небольшие таблицы; сейчас 76 правил; именно этот класс дал ошибку области действия |
| 3 | `Инструкция_по_продаже_миграционных_услуг_с_ценами.docx` | проза с ценами и условиями внутри абзацев, таблиц нет; сейчас 91 правило — проверка на условия и на «одно утверждение = одна запись» |

### 6.2 Эталон, собранный вручную

Эталон делает **человек, знающий услугу** (владелец или старший менеджер),
до и независимо от прогона модели. Формат — тот же JSON, но заполняются только
поля, которые человек может утверждать:

```jsonc
{ "documentId": "...", "goldFacts": [
  { "goldId": "g1",
    "statement": "Перевод с английского, тариф СТАНДАРТ, без нотариального заверения — 440 ₽",
    "factType": "price",
    "scope": { "service": ["translation"], "language": ["английский"] },
    "values": [ { "kind": "price", "amount": 440, "unit": "RUB", "tier": "СТАНДАРТ", "excludes": ["нотариальное заверение"] } ],
    "evidence": { "tableRef": { "tableIndex": 2, "rowHeader": "АНГЛИЙСКИЙ", "colHeader": ["СТАНДАРТ","С"] } },
    "audience": "client_safe",
    "critical": true }
] }
```

Объём эталона: для прайса не нужно расписывать все 1816 ячеек вручную —
берётся **полная матрица из `convertToHtml`** (она и есть эталон значений,
её достаточно один раз глазами подтвердить) плюс 20–30 ручных фактов на прозу
вокруг таблиц. Для документов 2 и 3 — по 30–40 фактов, из них помеченных
`critical: true` (цена, срок, запрет, орган подачи) должно быть не меньше 15.

Хранить в `docs/bot-audit/gold/<documentId>.json`.

### 6.3 Метрики (в порядке применения)

**Программные гейты — до всякой оценки смысла. Считаются скриптом, стоят 0 ₽.**

| № | Метрика | Как считается | Порог |
|---|---|---|---|
| G1 | **Проверяемость цитаты** | доля фактов, где `rawText.slice(charStart,charEnd) === evidence.quote` | **100 %**, иначе стоп |
| G2 | **Уникальность кода** | коллизий `ruleCode` после коммита | **0** |
| G3 | **Полнота области** | доля фактов с непустым `scope.appliesTo` | **100 %** |
| G4 | **Обоснованность `company_wide`** | доля фактов с `universality = company_wide`, у которых в цитате есть маркер всеобщности | ≥ 90 %, и сама доля `company_wide` ≤ 10 % |
| G5 | **Заземление чисел** | доля чисел из `values[]`, встречающихся в `evidence.quote` **и** в `rawText` | **100 %** |
| G6 | **Отсутствие внутренних противоречий** | пар фактов с идентичной областью и разными `values` — сверх заявленных в `conflicts[]` | **0** |

**Метрики качества относительно эталона.**

| № | Метрика | Формула | Порог |
|---|---|---|---|
| M1 | **Полнота (recall)** | найденных `goldFacts` / всех `goldFacts` | ≥ 95 % общий, **100 %** на `critical: true` |
| M2 | **Точность значений** | фактов с совпавшими `values.amount` и `unit` / сопоставленных | ≥ 99 % |
| M3 | **Точность выравнивания таблицы** | для прайса: ячеек, у которых верно определены `rowHeader` (язык) и `colHeader` (срок + «вкл. НЗ») / всех ячеек | ≥ 99 % (сверяется автоматически с HTML-матрицей) |
| M4 | **Точность области действия** | фактов, чей `scope` не шире и не уже эталонного / сопоставленных | ≥ 90 % |
| M5 | **Фрагментация** | извлечённых записей на один эталонный факт | 0,9 ≤ x ≤ 1,3 (сейчас для прайса — 199 правил на ~1816 ячеек и обратно: значения слиты) |
| M6 | **Точность аудитории** | совпадений `audience.proposed` с эталоном | ≥ 95 %, при этом ложных `client_safe` — **0** |
| M7 | **Ложные факты (precision)** | извлечённых записей, не соответствующих ни одному месту документа | **0** |

**Жёсткое вето вместо среднего.** Одна ошибка в `critical`-факте (неверная цена,
срок, орган подачи) или один ложный `client_safe` — прогон отклоняется целиком,
независимо от остальных цифр.

### 6.4 Процедура

1. Собрать эталон на 3 документа (человек, ~2–3 часа).
2. Прогнать новый пайплайн на этих 3 документах **в отдельную схему/таблицы**,
   не трогая прод.
3. Прогнать G1–G6 скриптом. Провал любого — правится пайплайн, эталон не трогается.
4. Прогнать M1–M7 автоматическим сопоставлением (по `values` и нормализованным
   цитатам), спорные пары — глазами.
5. Зафиксировать результат в `docs/bot-audit/gold/run-<дата>.md`.
6. Только после двух подряд зелёных прогонов — остальные 41 документ, партиями
   по 10, с теми же G1–G6 на каждой партии.
7. Старые правила не удалять до сверки: пометить `SUPERSEDED` и сравнить
   ответы бота на существующей батарее вопросов
   (`scripts/ask-battery-v2.mjs`, `scripts/live-corpus-run.mjs`) до и после.

### 6.5 Что сделать до переразбора и без модели

Порядок важен: три вещи ниже дешевле любого промпта и снимают часть дефектов
до того, как модель что-либо увидит.

1. **Парсер:** `mammoth.convertToHtml` + структурный экстрактор таблиц.
   Снимает потерю выравнивания (раздел 4) для 25 таблиц / 438 строк.
2. **Прайсы — детерминированно.** Матрица язык × тариф × «вкл. НЗ» разбирается
   кодом в структурные записи цен. LLM к прайсу не подпускается вовсе.
3. **`@@unique([ruleCode])`** и присвоение кода базой при коммите. Снимает
   класс ошибки «104 кода на три правила каждый» навсегда.

## 7. Сводка

**Вопросы.** Контракт из пяти полей (`ruleCode`, `title`, `body`, `confidence`,
`sourceSpan{quote,locationHint}`) не содержит ни области действия, ни условия,
ни даты источника, ни типа факта. Промпт прямо требует максимизировать полноту
(«лучше извлечь 30, чем пропустить 20»), содержит устаревший ценовой пример
(`630` против фактических `440`), классификатор доменов видит первые 8000
символов, а извлечение режет документ на батчи по 4500 символов, оставляя
последний батч прайса вообще без строк-заголовков.

**Классификация.** Аудитория — единственная работающая ось (0 расхождений),
но её гранулярность — файл, а не факт, и модель о ней не спрашивают.
Сценарий проставлен у 421 правила из 1967, и только пост-фактум скриптом по
имени файла; остальные 1546 с `scenarioKey = NULL` проходят через любой
сценарный фильтр. Домены стоят у всех правил по 3,84 штуки в среднем
(`pricing` — у 76,9 %) и **отключены при ответе**; 11 275 строк в четырёх
маппинг-таблицах не читаются. Типа правила не существует.

**Связывание.** 104 `ruleCode` дублируются (79 × 3 записи, 25 × 2), и все 104 —
это разные правила с одинаковым кодом. Механизм: номер берётся из
закоммиченных `ACTIVE`-правил, а извлечение пишет в `StagedExtraction`, поэтому
документы, обработанные до коммита предыдущего, получают один диапазон.
Уникальности в схеме нет. 114 активных правил без документа участвуют в
выборке, но исключены из списка источников. Позиции в документе нет ни у одного
правила (`charOffset` — 0 записей, `chunkId` — 0), связи `Rule ↔ DocChunk` нет
в схеме, а в блоке «Источники» показывается `body` правила, а не цитата.
14,4 % цитат (231 из 1609) не находятся в собственном документе даже поиском
подстроки. Версионирование правил мертво (0 записей с `version > 1`).

**Главный дефект контракта одной фразой:** модель просят пересказать документ,
а не привязать факт — поэтому у знания нет ни области, в которой оно верно,
ни адреса, по которому его можно проверить.
