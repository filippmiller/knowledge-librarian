## ПРОДУКТ И ГЛАВНОЕ ПРАВИЛО

Бюро переводов (СПб). Система отвечает менеджерам на вопросы по корпоративным
инструкциям: апостиль, переводы, нотариат, отправка. Продаётся корпоративным клиентам.

**Главное правило владельца: не подгонять метрику.** Зелёный отчёт при неверном
ответе — худший из возможных исходов. Если правка делает тест зелёным, не меняя
поведения по существу, — это вред, а не польза.

Определение верного ответа (все четыре планки обязательны):
1. верный текст; 2. верная ссылка на источник; 3. спрашивает уточнение при
неоднозначности; 4. **отказывается, когда не знает** — не выдумывает.

## ЗАДАЧА 1. `answerSource` врёт при отказе

**Файл:** `src/lib/ai/enhanced-answering-engine.ts`, около строки **1810**.

Основной возвратный путь жёстко проставляет `answerSource: 'knowledge_base'`.
Поэтому вопрос «сколько сейчас стоит биткоин» получает ПРАВИЛЬНЫЙ текст ответа
(«В базе знаний по этому вопросу нет данных») и при этом помечается как ответ
**из базы знаний**. `confidenceLevel` при этом `insufficient`.

Для корпоративного аудита («какие ответы пришли из наших документов») это переворачивает
смысл: отказ засчитывается как ответ по документам.

**Что сделать:** `answerSource` должен ОТРАЖАТЬ факт, а не путь в коде. Если ответ не
опирается ни на одну цитату — это не `knowledge_base`.

Тип поля (строка ~135): `'knowledge_base' | 'general_ai' | 'deterministic_guardrail'`.
Оракул ожидает для отказа `source: 'none'` (см. `scripts/eval/cases.json`, кейс про
биткоин). Значит либо расширяй union до `'none'`, либо обоснуй другое решение — но
тогда объясни, что именно должен видеть аудитор.

**Осторожно, это ловушка:** не выводи отказ по подстроке «нет данных» в тексте ответа.
Это подгонка под тест. Признак должен быть структурным — например отсутствие
использованных цитат / `insufficient` / пустой `primarySource`. Обоснуй выбор.

**Приёмка:** кейс с биткоином зеленеет ПОТОМУ ЧТО изменилась метка источника, а не текст.
Остальные 18 кейсов не деградируют.

## ЗАДАЧА 3. Детектор противоречия правила собственной цитате

**Файл:** `src/lib/document-processing/extraction-lint.ts` (существует, 4486 байт).

Его шапка гласит: «Non-blocking by design… The admin still decides». Он уже заявляет,
что ловит выдуманные адреса/числа, которых нет в собственной цитате правила — но
пропустил правило, где адрес Минюста назван «Исаакиевская площадь 11», тогда как
цитата того же правила говорит «ул. Оптиков, 35к1».

**Что сделать:**
1. Разберись, ПОЧЕМУ существующая проверка это пропустила. Это главная часть задачи —
   не пиши новый детектор, не поняв, почему сломан имеющийся.
2. Добавь `polarity_conflict`: тело утверждает P, а собственная цитата или собственный
   заголовок утверждают ¬P по ТОМУ ЖЕ стему (`требуется`, `нуж(ен|на|но)`, `можно`,
   `входит`). Сравнение по стему, не «есть ли где-то отрицание».

**ВАЖНОЕ ИЗМЕРЕНИЕ, которое меняет ценность этой задачи:** я замерил покрытие такого
детектора на проде — цитата и тело пересекаются по предикату «требуется» лишь в
**8 правилах из 1535 (0,5%)**. То есть детектор почти всегда будет молчать.
Скажи честно, стоит ли он свеч, и не правильнее ли вместо него проверять
**поддерживает ли цитата утверждение тела вообще**. Если да — предложи, как это
сделать детерминированно.

**Ловушка кириллицы (я на ней уже обжёгся):** `\b` в JS определён через ASCII `\w`,
поэтому `/\bтребуется\b/` в русском тексте **не срабатывает никогда** и молча даёт ноль
совпадений. Используй `(?<![а-яёa-z])стем(?![а-яёa-z])` с флагом `u`.

**Приёмка:** три фикстуры — (а) правило с инвертированным телом должно быть помечено;
(б) согласованные заголовок/цитата/тело — не помечено; (в) смешанное предложение
(«паспорт требуется, запись не требуется») при цитате про запись — не помечено.
