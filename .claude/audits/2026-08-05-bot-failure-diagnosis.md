# Диагностика: почему Telegram-бот отвечает «В базе знаний нет данных» почти на всё

Дата: 2026-08-05
Тип: диагностика (без правок кода)

## КОРНЕВАЯ ПРИЧИНА

**Anthropic не является причиной.** Ключ на проде исчерпан (тот же самый, что и локально — `sk-ant-api03-P_-5SU7FZYuR...`), и fallback на OpenAI в `chat-provider.ts` отрабатывает корректно на каждом шаге пайплайна — это подтверждено живыми прогонами (см. ниже).

**Настоящая причина — в `src/lib/ai/enhanced-answering-engine.ts`, функция `isBureauTopic()` (строки 2216–2233).** Классификатор сценариев (`classifyScenario`, LLM) знает только taxonomy апостиля. Любой вопрос вне этой taxonomy получает `out_of_scope`. Единственный «спасательный» механизм для остального содержимого базы (нотариат, переводы, оплата, доставка, IT, HR и т.д.) — жёстко заданный регэксп-список ключевых слов `BUREAU_TOPIC_PATTERN_CI`. Если вопрос не содержит НИ ОДНОГО слова из этого списка (апостиль, перевод, доверенность, свидетельство, справка, диплом, судим, паспорт, истреб, консульск, заверен, печат, штамп, загранпаспорт, гражданств, виз, опек, документ, миграц, внж, вид на жительство, рвп, содействи), поиск по базе НЕ ЗАПУСКАЕТСЯ ВООБЩЕ, и движок возвращает жёстко закодированную строку:

```
"В базе знаний нет данных по этому вопросу. Уточните, пожалуйста, о какой услуге идёт речь — апостиль, перевод, нотариальное заверение?"
```

(`buildOutOfScopeResult`, строки 2599–2619). Это происходит ДО ретрива, ДО эмбеддингов, ДО любого обращения к Anthropic/OpenAI — сама база знаний ни разу не спрашивается.

## Доказательства (живые прогоны на проде, `railway run npx tsx scripts/diagnose-answer.ts`)

| «Нужен ли апостиль для документов в Казахстан?» | out_of_scope → `isBureauTopic`=true → knowledge_lookup | 🟢 ИЗ ДОКУМЕНТОВ | 80% увер., корректный ответ с ценой/условиями |

## Подтверждение из прод-БД (таблица `HeldAnswer`, реальные вопросы пользователей 2026-08-03…08-05)

Прогнал `railway run node` со скриптом на `heldAnswer.findMany` — 8 последних удержанных ответов, ВСЕ 8 имеют `blocker: "confidence_level_too_low"`, `confidence: 0`, `answerSource: null`, и у ВСЕХ `draftAnswer` — это буквально та же строка «В базе знаний нет данных…». Среди них:

- «что делать при обнаружении ошибки?» — реальный вопрос сотрудника, тоже упёрся в `isBureauTopic`=false.
- «как оформить заказ онлайн?» — то же самое.
- «Ваше мнение, чего не нужно делать в офисе, в чатах?» — вопрос заказчика из задания. **Это корректный отказ**: вопрос действительно не про сущность из базы (не факт, не процедура, не цена), а личное мнение. Разбирать его отдельно не нужно.

Итого: у бота работает retrieval, работают эмбеддинги (OpenAI), работает синтез ответа (fallback на OpenAI) — но подавляющее большинство реальных прод-вопросов НИКОГДА до retrieval не доходит из-за узкого allow-list в `isBureauTopic`.

## Что РАБОТАЕТ (проверено напрямую)

1. **OpenAI ключ на Railway** (`OPENAI_API_KEY=sk-svcacct-Te6iUq0h2...`) — рабочий. Прямой вызов `POST https://api.openai.com/v1/chat/completions` с прод-ключом → HTTP 200, `gpt-4o` отвечает.
2. **OpenAI embeddings** (`text-embedding-3-small`) — рабочий, HTTP 200. Retrieval НЕ завязан на Anthropic вообще: эмбеддинги всегда идут через OpenAI (`src/lib/openai.ts`), Anthropic эмбеддингов не делает и в этом пути не участвует.
3. **Fallback Anthropic → OpenAI в `chat-provider.ts`** — работает штатно на каждом вызове (`classifyIntent`, `expandQuery`, `extractEntities`, `classifyScenario`, основной синтез, `consistency-gate`, `canonical-answer-polisher`). Все эти модули идут через единую функцию `createChatCompletion`, прямых вызовов Anthropic в обход неё в коде нет (проверено грепом по `api.anthropic.com` и `ANTHROPIC_API_KEY` — только в `chat-provider.ts`). Ошибка 400 «credit balance too low» НЕ входит в список retryable-кодов (`[429, 529, 503, 502]`), поэтому primary-провайдер падает быстро (без 3 бесполезных ретраев) и сразу уходит в fallback — задержка на вопрос минимальна, не единицы минут.
4. **Streaming-путь** (`streamChatCompletionTokens`, вызывается напрямую без общего fallback) используется только для обработки документов при загрузке (`knowledge-extractor-stream.ts`, `domain-steward-stream.ts`), НЕ для ответов в Telegram — значит поломанный Anthropic там не бьёт по Q&A.
5. `AISettings.autoAnswerEnabled = true`, `autoAnswerMinConfidence = 0.5` — автоответ включён, порог адекватный, это НЕ причина.

## Что СЛОМАНО

- **`isBureauTopic()` allow-list слишком узкий.** Реальные вопросы про заказ услуги онлайн, про внутренние процессы (что делать при ошибке), и, вероятно, любые вопросы про переводческие операции/доставку/IT без буквального упоминания «апостиль/перевод/…», никогда не доходят до поиска по базе. Это чисто маршрутизационный баг в коде, никак не связанный с балансом Anthropic.
- **`buildOutOfScopeResult` — тупиковая ветка без ретрая.** Даже если бы Anthropic работал идеально, при `out_of_scope && !isBureauTopic` ответ гарантированно «нет данных» — движок никогда не пробует открытый поиск как последний шанс.

## Второстепенная находка (не чинил, отдельная проблема)

В таблице `HeldAnswer` у 4 из 8 последних записей (все с меткой времени 2026-08-05 08:23–08:24 UTC) поле `question` побито в мусорные символы (replacement characters, `�`) — сам текст пользовательского вопроса нечитаем в БД, при этом `draftAnswer` (захардкоженная строка в коде) сохранился нормально. Это похоже на реальную порчу кодировки при приёме сообщения из Telegram (не артефакт консоли — проверено через файловый дамп в UTF-8, не через терминал). Если это так, это ВТОРОЙ независимый баг: побитый текст вопроса не матчится ни по `isBureauTopic`, ни осмысленно классификатором — тоже даёт «нет данных», но по другой причине. Стоит отдельного расследования (найти, где в `src/lib/telegram/*` текст входящего апдейта проходит через что-то, способное испортить кодировку — например, повторную сериализацию не-UTF8-совместимым путём). Не входило в объём этой задачи, править не стал.

## Что НЕ является багом

Отказ на вопрос заказчика «Ваше мнение, чего не нужно делать в офисе, в чатах?» — корректное поведение: вопрос не про факт/процедуру/цену из базы, а личное мнение. Такой же результат («нет данных», confidence 0) дал бы и полностью исправный бот.

## Рекомендация (для отдельной задачи на исправление, не для этой)

Расширить `isBureauTopic()` / сам гейт `out_of_scope`, чтобы вопросы, не подходящие ни под taxonomy апостиля, ни под текущий keyword-список, всё равно проходили через `knowledge_lookup` (открытый поиск), а не мгновенно возвращали «нет данных» — то есть менять политику с allow-list на «пробуем открытый поиск, и только если поиск реально ничего не нашёл — тогда честное „нет данных“». Это меняет самую суть текущей защиты (специально узкий белый список, чтобы не расширять зря scenario retrieval), так что нужно отдельное решение владельца, а не автоматическая правка.
