# Аудит качества извлечения базы знаний — 2026-08-05

Вопрос владельца: правила и Q&A могли быть извлечены слабыми моделями (система
старше Opus 5) и извлечены плохо — нужно ли переизвлекать всё заново?

Метод: не гадать, измерить. Инвентаризация прод-базы (Railway Postgres) +
глубокий разбор 3 документов + одно контрольное переизвлечение через gpt-4o +
проверка живучести трёх известных дефектов из истории проекта.

---

## 1. Инвентаризация

```
Documents: 44 (все parseStatus = COMPLETED)
Rules:     1967 всего → 1535 ACTIVE (78%) / 238 SUPERSEDED (12%) / 194 DEPRECATED (10%)
QAPairs:   743
Суммарный объём исходного текста корпуса: 174 597 символов, 44 документа, среднее 3968 симв/документ
```

**Провенанс модели — НЕ ЗАПИСАН нигде.** В схеме (`prisma/schema.prisma`) ни у
`Rule`, ни у `QAPair`, ни у `StagedExtraction` нет поля model/promptVersion/
extractedAt. `AISettings.model = "gpt-4o"` — это ТЕКУЩАЯ настройка, а не история:
по ней нельзя понять, какой моделью извлечено конкретное правило. Это само по
себе находка: **у команды физически нет данных, чтобы подтвердить или
опровергнуть гипотезу «извлекала слабая модель»** — только косвенные признаки
(id-коды правил, даты документов).

Косвенный признак того, что переизвлечение УЖЕ проводилось: у нескольких
документов ruleCode делает скачок (напр. `Инструкция оформление Апостиля в
МинЮсте`: R-1…R-61 все `SUPERSEDED`, следом R-395…R-470 `ACTIVE`) — то есть
пайплайн уже перезапускался на части документов текущей версией, не факт, что
это «древняя слабая модель, тронутая один раз».

**Распределение правил по документам** — плотность (правил на 1000 символов
исходника) резко скачет у процедурных апостильных инструкций:

| Документ | правил/1000 симв | ACTIVE / всего |
|---|---|---|
| Инструкция оформление Апостиля в МинЮсте | 23.97 | 76/137 |
| Инструкция по оформлению Апостиля в МВД | 23.75 | 59/111 |
| Инструкция оформление Апостиля в ЗАГСе | 23.30 | 55/107 |
| Инструкция оформление Апостиля в ЗАГС по ЛО | 20.53 | 49/96 |
| Прайс на перевод и заверение-010126 | 13.20 | **15/199** (уже почищено, см. §4) |

Списки стран (`Список_стран…КЛ`, 86.7 правил/1000 симв) не считаю дефектом —
это буквально список из ~50 стран, одна страна = одно правило, оправданная
гранулярность. А вот апостильные инструкции — это ~5 документов, где почти
КАЖДОЕ предложение стало отдельным правилом, включая расписания по дням недели
дважды подряд (старый проход + новый), что и объясняет 40-46% SUPERSEDED/
DEPRECATED долю именно в этой группе документов.

## 2. Глубокий разбор (2 документа прочитаны целиком: исходник + все правила + Q&A)

### 2.1 «Инструкция оформление Апостиля в МинЮсте» (5715 символов, 76 ACTIVE правил, 41 ACTIVE Q&A)

Подтверждённые дефекты на живых данных:

- **Точный дубль внутри ACTIVE-набора**: R-448 и R-454 — дословно одно и то же
  правило («если клиент не знает, куда ставить апостиль…») с разными title.
  Не единичный случай — см. §4 (26 кластеров точных дублей тела правила по
  всей базе).
- **Подтверждён дефект «частный случай записан как общее правило»**:
  правило **R-417** «Три маршрута исходника нотариального перевода» утверждает
  ТРИ варианта источника перевода (простая ксерокопия / нотариальная копия /
  оригинал), но цитата-источник (`sourceSpan.quote`) для ЭТОГО документа
  содержит только ДВА: *«Перевод может быть подшит к нотариальной копии или к
  оригиналу документа»*. Третий вариант («простая ксерокопия») подмешан из
  другого, более общего документа о нотариальном переводе — то есть общее
  утверждение из соседнего документа было записано как будто оно взято из
  ЭТОГО источника. Ровно тот класс дефекта, который описал владелец.
- Расписания по дням недели продублированы между старым (SUPERSEDED, R-42…R-51)
  и новым (ACTIVE, R-453/R-460…R-468) проходом извлечения — это не потеря
  данных, а дважды потраченные строки на одно и то же.

Q&A-пары: 41 ACTIVE, по содержанию корректны и опираются на текст; явных
галлюцинаций не найдено (в отличие от Rule-слоя).

### 2.2 «Прайс на перевод и заверение Наливайко М.В. 01012026» (80/80 ACTIVE правил)

Этот документ — «сиблинг» уже почищенного `Прайс на перевод и заверение-010126`
(тот самый пилотный документ из коммита `13b59ab`, где 184 дубля тарифной сетки
погашены). **Чистка не была распространена на этот второй прайс-документ той же
серии**: 52 из 80 ACTIVE-правил — это ровно те же дубли построчной языковой
матрицы («Тарифы на перевод с X языка, категория N»), которые механически
проверяются против `Tariff` (см. §4). Т.е. известная, уже решённая проблема
осталась нерешённой на соседнем документе — не новый класс дефекта, а
недоведённая до конца предыдущая работа.

### 2.3 Прочее (беглый обзор, не читал целиком)

«Список_стран…КЛ» и «Страны…не нужен апостиль» — высокая плотность правил, но
по устройству документа (построчный список стран) это ожидаемо и не является
дефектом извлечения.

## 3. Контрольное переизвлечение (gpt-4o)

Документ: «Инструкция оформление Апостиля в МинЮсте» (5715 симв, самый спорный
кейс из §2.1). Промпт явно требовал: не обобщать частные случаи в общие
правила, не терять по-дневную детализацию расписаний, извлекать все
процедурные шаги.

**Результат:**

```
В базе (ACTIVE):                 76 правил + 41 Q&A = 117 единиц знания
gpt-4o, один проход (8000 ток.):  13 консолидированных фактов
Новых фактов сверх базы:          0
Фактов из базы, отсутствующих
  в gpt-4o-выдаче:                ~15 (весь 11-шаговый чек-лист процедуры,
                                   объяснение смысла штампа апостиля,
                                   политика консультирования клиента)
```

Токены одного прохода: 2052 prompt + 1939 completion = 3991 total (см.
`scratchpad/minjust-reextracted.json`). При такой плотности gpt-4o, наоборот,
**консолидировал** факты (объединил все дни недели в одно поле body) вместо
атомарного дробления — то есть с наивным промптом современная модель не
«находит больше», а меняет гранулярность и ТЕРЯЕТ часть процедурного/
объяснительного контента, который в базе сейчас есть.

**Вывод из этого эксперимента**: гипотеза «переизвлечение современной моделью
найдёт значительно больше фактов» на этом (худшем по плотности дублей)
документе НЕ подтвердилась. Слепой один проход gpt-4o дал 0 новых фактов и
меньшее покрытие, чем то, что уже лежит в базе. Это не доказывает, что вся
база хорошего качества — но опровергает предположение, что «любое
переизвлечение современной моделью автоматически лучше».

Оговорка: это упрощённый одиночный промпт, а не воспроизведение 3-фазного
прод-пайплайна (классификация домена → извлечение → чанкинг). Результат нижняя
оценка усилий, а не окончательный вердикт по качеству возможного полного
переизвлечения с более аккуратным промптом.

## 4. Известные дефекты — живы ли сейчас

### 4.1 «Потеря языка в ценовых правилах» — ОПРОВЕРГНУТО (подтверждена прошлая находка)

Проверено на 3 языках (чешск-, шведск-, таджикск-): язык присутствует в
`Rule.title` в 100% найденных случаев («Тарифы на перевод с чешского языка,
категория 1» и т.п.). Претензия «107 из 160 правил без языка» не
воспроизводится — язык не терялся, он лежит в title, как и было установлено
ранее.

### 4.2 Дубли — ЧАСТИЧНО ЖИВЫ

184 дубля погашены, но **только на одном пилотном документе** (`Прайс на
перевод и заверение-010126`, 199→15 ACTIVE). Апостильные инструкции (МинЮст/
МВД/ЗАГС/ЗАГС ЛО) получили частичную чистку через повторный проход пайплайна
(40-46% в SUPERSEDED/DEPRECATED), но не полную.

**Остаток дублей по всей базе (ACTIVE-правила, посчитано скриптом):**

```
Точные дубли ТЕЛА правила:   26 кластеров, 52 избыточные строки
Точные дубли ЗАГОЛОВКА:      79 кластеров, 115 избыточных строк
Непочищенная языковая матрица
  тарифов (сиблинг-документ): 52 строки («Прайс…Наливайко М.В. 01012026»)
```

Итого не менее **~167 избыточных ACTIVE-строк** правил подтверждённо дублируют
либо друг друга, либо тарифную сетку — механически проверяемо, без LLM.

### 4.3 Противоречия («нужен ли оригинал») — НЕ ОБНАРУЖЕНЫ в текущем срезе

`scripts/audit-corpus-contradictions.ts` нашёл 34 ACTIVE эталонных Q&A-пары
(voice-operator/historical-operator authority), затрагивающих узел
«оригинал/подшивка». Из них 4 явно классифицируются скриптом по паттерну
«обязателен оригинал» vs «копии достаточно» — **все 4 сейчас на стороне
«копии достаточно, зависит от получателя»**, взаимоисключающих пар не найдено.
Историческая история «4 противоречащие пары» для этого конкретного узла
похоже уже решена — но проверка ограничена одним паттерном на Q&A-слое с
operator-authority тегами, не полным перебором 1535 ACTIVE правил на предмет
противоречий в принципе.

## 5. Вердикт

**ТОЧЕЧНАЯ починка, не полное переизвлечение.**

Обоснование числами:

1. Ни один из трёх проверенных «страшных» дефектов не подтвердился в масштабе,
   который оправдывал бы полный передел: язык не терялся (§4.1), заявленная
   4-контрадикция не воспроизводится (§4.3), а найденный реальный дефект
   («частный случай как общее правило») подтверждён лишь на 1 правиле из
   76 прочитанных вручную — не исключено, что таких случаев больше по базе,
   но массового явления в прочитанных документах не видно.
2. Контрольное переизвлечение gpt-4o на самом плотном/спорном документе дало
   **0 новых фактов и меньшее покрытие**, чем уже лежит в базе (§3). Слепой
   передел не гарантированно лучше — а по этому эксперименту прямо хуже без
   тщательного промпт-инжиниринга.
3. Настоящая, измеримая проблема — **дубли** (167+ строк ACTIVE, §4.2), причём
   рецепт починки уже существует и один раз сработал (`retire-matrix-
   duplicate-rules.ts`), просто не был докручен до конца.

**Рекомендованные действия (по цене восходяще):**

1. **Прогнать существующий retire-matrix-duplicate-rules.ts (с поправкой на имя
   файла) на «Прайс на перевод и заверение Наливайко М.В. 01012026»** — те же
   52 строки того же класса дублей, механика уже проверена и безопасна.
   Стоимость: минуты, без LLM.
2. **DB-wide зачистка точных дублей тела/заголовка** (26+79 кластеров) —
   детерминированный скрипт (используй `scratchpad/dedup-and-status.ts` как
   основу), без LLM, с ручной проверкой перед `DEPRECATE`. Стоимость: часы
   разработки скрипта + ревью, без API-затрат.
3. **Добавить в схему провенанс извлечения** (`Rule.extractionModel`,
   `extractionPromptVersion`, возможно `extractedAt` отдельно от `createdAt`)
   — чтобы следующий такой аудит не начинался с «мы не знаем, чем это
   извлечено». Дешёвая миграция, отсутствие которой — сама по себе находка
   этого аудита (§1).
4. **Точечная проверка «общее вместо частного»** — не полное переизвлечение, а
   дешёвый классификатор: прогнать каждое ACTIVE-правило (1535 шт.) через
   gpt-4o-mini/haiku с промптом «выходит ли body за пределы того, что
   утверждает quote — да/нет + почему», получить приоритизированный список
   подозрительных правил для точечного ревью человеком. Оценка стоимости по
   корпусу: суммарный объём исходников 174 597 символов ≈ 63 000 входных
   токенов на один проход всего корпуса (по измеренному соотношению
   2052 ток./5715 симв.); классификация 1535 коротких правил на дешёвой модели
   — по грубой оценке $2-5 суммарно. На порядок дешевле и куда прицельнее, чем
   передел всей базы.

**Оценка стоимости ПОЛНОГО переизвлечения (если бы решили делать), для
сравнения:** 174 597 символов корпуса ÷ 2.78 симв/токен (измеренное
соотношение) ≈ 63 000 входных токенов на один проход всего корпуса через
gpt-4o; при сопоставимом объёме вывода (по измеренному кейсу completion ≈ 0.95×
prompt) — ещё ≈ 60 000 выходных токенов. По цене gpt-4o (~$2.5/1M вход,
~$10/1M выход) это **меньше $1 за один грубый проход всего корпуса**, то есть
деньги на переизвлечение — не аргумент против. Аргумент против — доказанный в
§3 риск: наивный проход гpt-4o консолидирует и теряет процедурный контент, а
не улучшает его. Если полное переизвлечение когда-то понадобится, оно требует
многофазного промпта (отдельно структурные поля / отдельно процедуры и
пояснения), сверки с `Tariff` как источником истины по ценам и обязательной
записи провенанса — не слепой замены.
